# CommitCity — Art Direction

| | |
|---|---|
| **Status** | Draft — Phase 0 (Discovery & Specification) |
| **Audience** | Pixel artists, designers, and developers working on rendering or assets |
| **Related docs** | [`VISION.md`](./VISION.md), [`ARCHITECTURE.md`](./ARCHITECTURE.md), [`CONTRIBUTING.md`](../CONTRIBUTING.md) |

This document defines **how CommitCity looks** and the **technical rules every sprite must follow** so that art from many contributors fits together in one city.

Each rule is marked as:

- **Rule** — must be followed for an asset to be accepted.
- **Guideline** — strongly recommended; reviewers may ask for changes.
- **Proposal** — not final; will be validated by the first technical milestone (see `ROADMAP.md`).

> **Originality.** TheoTown is our primary *visual reference* for mood, density, and level of detail. CommitCity never copies, traces, edits, extracts, or redistributes TheoTown assets, and never uses "TheoTown" as an input to image-generation tools. All assets must be original or properly licensed.

---

## 1. Aesthetic goals

What a CommitCity screenshot should feel like:

- **Dense and alive.** Streets, buildings, trees, and small props fill the space. Empty grass is a deliberate choice, not a default.
- **Readable at a glance.** Building size, style, and condition must be recognizable at the default zoom without reading any label.
- **Warm and cozy.** Slightly saturated colors, soft contrast, friendly shapes. Not gritty, not neon.
- **Coherent.** Every asset looks like it was drawn by the same hand, with the same palette, light, and outline rules.
- **Handmade.** Hard pixels, deliberate clusters, no blur, no photographic texture.

## 2. Projection

| Item | Specification | Status |
|---|---|---|
| Projection | **2:1 pixel dimetric** ("pixel isometric"): every diagonal edge moves 2 px horizontally for each 1 px vertically. | Rule |
| Vertical edges | Exactly vertical. | Rule |
| Free angles | None. Only horizontal, vertical, and 2:1 lines are allowed for structural edges. | Rule |
| Camera | Fixed elevation. The view can rotate only in 90° steps (later). | Rule |

The world is a square grid. Tile `(x, y)` is drawn at screen position:

```
screenX = (x - y) * (TILE_WIDTH / 2)
screenY = (x + y) * (TILE_HEIGHT / 2)
```

## 3. Tiles

| Item | Specification | Status |
|---|---|---|
| Base tile size | **32 × 16 px** diamond (width × height). | Confirmed |
| Diamond shape | Drawn inside a 32 × 16 box; top and bottom vertices are 2 px wide, left and right vertices are 1 px tall, following the 2:1 step. | Rule |
| Height unit | Heights are measured in pixels above the tile surface. One building storey ≈ **8 px**. | Guideline |
| Rendering scale | Assets are authored at **1×** and displayed at integer zoom levels (1×, 2×, 3×, 4×). The default view is expected to be 2× or 3×. | Rule |

**Why 32 × 16 (and not 64 × 32)?** A 32 × 16 tile matches the dense, small-scale look of the reference and keeps the art effort per building low, which matters for a project without a dedicated artist yet. 64 × 32 allows more detail but roughly quadruples the pixels per building. Milestone 1.1 rendered both sizes with placeholder art, and 32 × 16 was confirmed on 2026-10-09 ([report](reports/milestone-1.1-rendering-spike.md)).

## 4. Sprite specification

### 4.1 Footprints

| Item | Specification | Status |
|---|---|---|
| Allowed footprints (current scope) | **Square only**: 1×1, 2×2, 3×3, 4×4 tiles. | Rule |
| Rectangular footprints | Not allowed in current scope; they complicate rotation and depth sorting. | Rule |
| Occupancy | A building must not draw outside its footprint, except upward (height) and small overhangs ≤ 2 px. | Rule |

### 4.2 Canvas and anchor

For a building with an `N × N` footprint and a visual height of `H` px:

```
canvas width  = N * 32
canvas height = N * 16 + H
anchor        = bottom-center pixel of the canvas
              = the bottom (front) vertex of the footprint diamond
```

- The footprint diamond sits at the **bottom** of the canvas, filling the full width. **Rule.**
- `H` is the height of the tallest pixel above the diamond's top vertex, rounded up to a multiple of **4 px**. **Rule.**
- No empty padding above the tallest pixel. **Rule.**

Example: a 2×2 building, four storeys (≈ 32 px of wall plus roof) → canvas `64 × (32 + 40) = 64 × 72`.

### 4.3 File format

| Item | Specification | Status |
|---|---|---|
| Format | PNG, RGBA, 1× scale (never upscaled). | Rule |
| Transparency | Hard alpha only: every pixel is fully transparent or fully opaque. | Rule (current scope) |
| Colors | Only colors from the project palette (see §6). | Rule |
| Atlases | Artists deliver individual PNGs. Texture atlases are generated by tooling. | Rule |
| Shadows | Drawn as opaque palette pixels inside the footprint; no semi-transparent drop shadows. | Rule (current scope) |

## 5. Light and shading

| Item | Specification | Status |
|---|---|---|
| Light direction | **Fixed in screen space, from the upper left.** | Rule |
| Face shading | Top faces lightest, **left-facing walls medium**, **right-facing walls darkest**. | Rule |
| Ramps | Each material uses a 3–5 step ramp from the palette (highlight → base → shadow → deep shadow). | Guideline |
| Hue shifting | Shadows shift slightly toward cool hues, highlights toward warm hues. | Guideline |

Because the light is fixed relative to the **screen**, a building drawn for one view **cannot be mirrored** to produce another view: mirroring would move the bright wall to the wrong side. See §8.

## 6. Palette

| Item | Specification | Status |
|---|---|---|
| Master palette | One shared palette for the whole project, **≤ 64 colors**, stored in the repository as `.gpl` (GIMP/Aseprite) and `.hex` files. | Rule |
| Starting point | **[Resurrect 64](https://lospec.com/palette-list/resurrect-64) by Kerrie Lake**, unchanged, in `assets/palette/`. It has ramps for brick, glass, concrete and vegetation. The palette page states no formal license; its author allows use in commercial games, and a list of colors is generally not copyrightable (`assets/palette/README.md`). | Confirmed (milestone 4.1) |
| Changes | Adding or changing palette colors requires a dedicated pull request and maintainer approval. | Rule |
| Pure black / white | Avoided. Outlines and highlights use palette colors. Resurrect 64 includes `#ffffff`; use it only for small sparkles. | Guideline |
| Enforcement | `pnpm validate-assets` rejects any opaque pixel whose color is not in `commitcity.hex`. | Rule |

## 7. Line and detail rules

- **Outlines**: dark, colored outlines (darkest shade of the adjacent material), 1 px. Inner edges may be softer or omitted ("selective outlining"). **Guideline.**
- **No anti-aliasing** against transparency. Internal manual AA is allowed sparingly. **Rule.**
- **No jaggies**: diagonal lines follow a clean 2:1 step pattern. **Rule.**
- **No orphan pixels or noise textures**; detail comes from intentional clusters (windows, signs, AC units, roof tiles). **Guideline.**
- **Windows** are the main scale cue: keep window size and spacing consistent across all buildings (proposal: 2×3 px windows with 2 px spacing at 32 × 16). **Guideline.**
- **No text** in sprites (it cannot be translated and does not survive rotation). Logos and letters are abstract shapes only. **Rule.**

## 8. Directional sprites and rotation

Four-direction rotation is **deferred** (see `VISION.md`), but assets must be ready for it.

| Item | Specification | Status |
|---|---|---|
| Views | A building may provide up to four views: `0`, `1`, `2`, `3` (the view orientation, rotating 90° clockwise each step). | Rule |
| Required views (current scope) | **View `0` only.** | Rule |
| Required views (once rotation ships) | All four views for buildings. | Proposal |
| Fallback | If a view is missing, the renderer uses the nearest available view of the same building. A building never disappears. | Rule |
| Mirroring | **Not allowed for buildings** (breaks lighting, §5). Allowed for vegetation, small props, and ground decals, where the error is not noticeable. | Rule |
| Symmetric buildings | A building whose four sides are identical may reuse a single drawing for all views; it must declare this in its manifest (`"symmetric": true`). | Rule |
| Ground and roads | Ground and road tiles are rotation-safe by design: road shapes are chosen from neighbors on the rotated grid (auto-tiling), so one road set covers all views. | Proposal |

Each new view of a building is redrawn, not transformed. Plan for this effort when designing a building: simpler, more symmetric silhouettes are much cheaper to rotate.

## 9. Building families and proportions

Buildings are grouped in **families** that share materials, roof styles, and color ramps. Families map to districts (the mapping from repository language to district is defined in `ARCHITECTURE.md`).

Proposed initial families:

| Family | Look | Typical footprints |
|---|---|---|
| `residential` | Houses and small apartment blocks, pitched roofs, gardens | 1×1, 2×2 |
| `brick` | Brick offices and shops, flat roofs with AC units | 1×1, 2×2 |
| `modern` | Glass and concrete offices, towers | 2×2, 3×3 |
| `industrial` | Warehouses, chimneys, tanks | 2×2, 3×3 |
| `civic` | Large landmark buildings (domes, columns) | 3×3, 4×4 |

### 9.1 Levels and size

| Concept | Visual rule | Status |
|---|---|---|
| **Level** (activity) | Higher levels are taller and more detailed within the same footprint. Levels 1–3 per building type in current scope. | Proposal |
| **Footprint** (stars) | More significant repositories use larger footprints. | Proposal |
| **Max height** | ≈ 4× the canvas width, to keep towers from hiding large parts of the city. | Guideline |

### 9.2 Variants

| Variant | Meaning | Visual rule | Status |
|---|---|---|---|
| `default` | Active repository | Normal sprite | Rule |
| `abandoned` | Archived repository | Same silhouette, boarded windows, faded and desaturated colors, weeds | Rule |
| `annex` | Fork | One footprint size smaller than the equivalent original, simpler details | Proposal |

## 10. Ground, roads, and vegetation

- **Ground tiles**: grass, dirt, pavement (current scope); water and shoreline later. Each with 2–4 random variants to avoid repetition. **Guideline.**
- **Roads**: one small road type in current scope. Auto-tiled with a 4-bit neighbor mask (16 shapes: straight, corner, T-junction, crossing, dead end, isolated). **Proposal.**
- **Vegetation**: trees and bushes on 1×1 tiles, several species and sizes; they may slightly overlap neighboring tiles visually but never the footprint of a building. **Guideline.**
- **Props**: benches, lamps, fences, small signs. Optional decoration chosen deterministically by the generator. **Later.**

## 11. Animation

No animation is required in current scope. When animation arrives:

| Item | Specification | Status |
|---|---|---|
| Style | Frame-by-frame, short loops, 2–8 frames. | Guideline |
| Frame rate | Low and consistent: 4–8 fps. | Guideline |
| Subtlety | Small elements only: smoke, flags, blinking lights, water. Buildings themselves never move. | Rule |
| Night lights | Delivered as a separate **lights overlay** PNG with the same canvas as the base sprite, containing only lit windows and lamps. | Proposal |
| Frames layout | One horizontal strip per animation, equal frame sizes. | Guideline |

## 12. Asset structure and manifest

Every building is a folder containing its sprites and a manifest. This is what allows artists to add buildings **without changing code**.

```
assets/
  palette/
    commitcity.gpl
    commitcity.hex
  buildings/
    brick-office-small/
      manifest.json
      view-0.png
      view-0.abandoned.png
  ground/
  roads/
  vegetation/
```

Sprite files are named `view-<v>.png` for the `default` variant and `view-<v>.<variant>.png` for the others, for example `view-0.abandoned.png`. One drawing covers every level listed in `levels`; draw a second building folder when a level needs a different look. A symmetric building provides view 0 only. A folder must contain exactly the files its manifest declares. **Rule.**

Example `manifest.json` (the exact schema is defined in `ARCHITECTURE.md`):

```json
{
  "id": "brick-office-small",
  "family": "brick",
  "footprint": 2,
  "levels": [1, 2],
  "views": ["0"],
  "symmetric": false,
  "variants": ["default", "abandoned"],
  "authors": ["Jane Doe"],
  "license": "CC-BY-SA-4.0",
  "aiAssisted": false
}
```

### 12.1 Automatic checks

`pnpm validate-assets` runs in CI on every pull request and lists every problem with the file, the first offending pixel, and what to change. It checks:

- the manifest: every field present, no unknown fields, valid values, `id` equal to the folder name, license `CC-BY-SA-4.0`;
- the files: every declared PNG exists, nothing undeclared;
- the canvas: width `N × 32`, height `N × 16` plus a multiple of 4, at most 3 empty rows on top (§4.2);
- occupancy: nothing drawn below the footprint's lower edges, beyond a 2 px overhang (§4.1);
- hard alpha and palette colors (§4.3, §6).

`pnpm pack-assets` (run automatically by `pnpm dev` and `pnpm build`) packs valid buildings into an atlas, and the dev city at `/dev/city` uses them right away, next to the placeholders.

## 13. Placeholder art

Until real art exists, the renderer uses **code-generated placeholders**: simple boxes that follow this document exactly (32 × 16 tiles, 2:1 edges, three-tone face shading, palette colors, correct canvas and anchor). Placeholders let development continue without art and prove that the geometry rules work.

## 14. AI-assisted art workflow

The project has no pixel artist yet. AI image tools may be used to **draft** assets, under the rules below. AI output is treated as a starting point, never as a finished asset.

### 14.1 Tools

| Tool type | Use | Notes |
|---|---|---|
| General image models (for example ChatGPT image generation) | Concepts, mood, building ideas | Output is "pixel-art style", not real pixel art. Needs heavy cleanup. |
| Pixel-art-specific generators (for example PixelLab, Retro Diffusion) | Drafts closer to final assets | Evaluate first: they target real pixel grids and limited palettes. |
| Pixel editors (Aseprite, LibreSprite, Pixelorama) | Cleanup and final pass | Required for every AI-assisted asset. |

### 14.2 Base prompt

Use the same base prompt for every asset and change only the bracketed part. Do not name any existing game, studio, or artist.

```
Isometric pixel art building sprite, 2:1 dimetric projection, for a cozy
city-builder game. [A small 3-floor red-brick office building on a 2x2 tile
footprint, flat roof with AC units.] Light from the top-left: roof lightest,
left wall medium, right wall darkest. Limited palette (max 32 colors), crisp
1px dark colored outlines, no anti-aliasing, no gradients, no blur, no text,
no ground, no drop shadow. Single object centered on a solid #FF00FF
background. Hard square pixels, as if drawn at 64x72 pixels and upscaled 8x
with nearest-neighbor.
```

Tips:

- Generate several options and pick the one with the cleanest 2:1 edges.
- For an abandoned variant, start from the cleaned default sprite and edit it by hand instead of generating a new image; this keeps the silhouette identical.

### 14.3 Cleanup steps

1. **Remove the background** (the `#FF00FF` color) to transparency.
2. **Downscale** to the target canvas size (§4.2) using **nearest-neighbor** only.
3. **Map to the project palette** (§6); remove any color not in it.
4. **Fix the geometry**: redraw diagonal edges to a clean 2:1 step, make vertical edges straight, align the footprint to the diamond.
5. **Fix the shading** to match §5 (top lightest, left medium, right darkest).
6. **Fix outlines and noise** (§7): remove stray pixels, AA against transparency, and fake text.
7. **Check it in context**: place it next to existing assets at 1× and 2×.

### 14.4 Transparency and licensing policy

- Every AI-assisted asset sets `"aiAssisted": true` in its manifest and names the tool used in its pull request. **Rule.**
- Contributors must have the right to submit the output under the tool's terms of service. **Rule.**
- The copyright status of AI-generated images is legally uncertain in many places. Hand-drawn art is preferred, and **AI-assisted assets may be replaced** at any time by hand-drawn versions. **Rule.**
- Prompts must not reference existing games, studios, or artists by name. **Rule.**
- Assets are licensed under **CC BY-SA 4.0**, like all other artwork (details in `CONTRIBUTING.md`).

## 15. Asset review checklist

A reviewer checks every new asset against this list:

- [ ] Uses only palette colors and hard alpha.
- [ ] Authored at 1×; canvas and anchor follow §4.2.
- [ ] Square footprint, no drawing outside it (except height and ≤ 2 px overhang).
- [ ] Clean 2:1 diagonals and straight verticals.
- [ ] Light from the upper left; correct face shading.
- [ ] Outlines, windows, and detail density consistent with existing assets.
- [ ] No text, no references to existing games or brands.
- [ ] Manifest present and complete (authors, license, `aiAssisted`).
- [ ] Looks right next to existing assets at 1× and 2×.

## 17. Open questions

1. Is 32 × 16 detailed enough for buildings to be recognizable, or do we need 64 × 32? *(Answered: 32 × 16, Milestone 1.1.)*
2. Which palette do we adopt, and does it have enough material ramps (brick, glass, concrete, vegetation)? *(Answered: Resurrect 64, milestone 4.1.)*
3. How many building types are needed for a city to feel varied? Initial guess: 2–3 per family and footprint.
4. Do pixel-art-specific AI tools produce consistent enough results to be worth using, compared with drawing simple buildings by hand?
